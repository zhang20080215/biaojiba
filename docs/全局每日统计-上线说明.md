# 首页统计：每天一次，第一个访客触发

2026-10-25。本说明替代 2026-10-14 的「每个榜单滚动 24 小时、客户端逐个触发」方案。

## 旧方案的问题

- 每个榜单各自按 updatedAt 滚动 24 小时过期，一天里不同时刻陆续过期，被不同访客分别刷新。
- 没有锁：并发访客拿到同一份 refreshIds，各自把聚合跑一遍，写库时才发现被别人写过而丢弃。
- 由客户端逐个发 refreshStats（32 个榜单就是 32 次调用），用户中途离开就留给下一个人，「第一个用户」变成「一串用户」。
- 失败的榜单不写库，当天每个访客都会再查一次。
- 客户端每次 onShow 都调云函数，本地已有今天的数据也不用。

## 现在的流程（cloudfunctions/getThemeHub/statsCache.js）

- 以北京时间自然日为单位，theme_hub_cache/public-v1 记 `day: 'YYYY-MM-DD'`。
- `day` 是今天：直接返回 rows，不扫 theme_registry、不查标记、不写库。
- 不是今天：事务抢锁（`refresh: { day, lockUntil, token, done }`）。抢到锁的访客**立即拿到昨天的数据**，响应里多一个一次性 `refreshToken`，不用等统计。
- 客户端拿到令牌后，不等待地发起 `computeStats(token)`，统计在这次调用里按 4 并发跑完。只有持有当前锁令牌的调用才会真正查库，伪造或过期的令牌直接拒绝。
- 其他人同时进来也立刻拿到昨天的数据（响应带 `refreshing: true`、没有令牌），不触发查询。
- 客户端没发出 computeStats（比如刚拿到令牌就杀掉进程）：锁 70 秒后过期，下一个访客重新领令牌。
- 每算完一个榜单就落库并记入 `done`，函数被杀也不丢进度。超过 40 秒预算不再开新榜单，释放锁，剩下的由下一个访客接着算；持锁者被杀时锁 70 秒后过期，可被接手。
- 全部榜单处理完，写 `day = 今天` 并删除 `refresh`。
- 失败的榜单保留旧值，同样记入 done，当天不再重试，第二天再算。
- 人数口径同线上旧版：标记过该榜单任一作品的去重 openid 数。单条聚合超时（豆瓣 TOP250 约 458 万条标记，云函数里约 6 秒即 -501001 DATABASE_TIMEOUT，2026-10-25 compareStats 实测）时，按 openid 字符区间切 17 段分别去重再相加（每个用户只落一段，结果精确）；某段仍超时再拆成单字符段。依赖 Marks/BookMarks 上有 openid 索引。
- 不再用「标记条数 ÷ 3」估算（豆瓣人均约 90 部，曾估出 152 万）。算不出来就保留上次真实值；若旧值本身是估算值则删除，不显示。
- 查询期间有人在控制台手改了某一行，手改优先。但人工录入值只在当天有效，第二天会被重新统计覆盖。
- 当天新上线的云端主题要到第二天才有人数（当天不再扫注册表）。
- `refreshStats` 动作保留，等同于 `stats`，不再按调用方传入的 theme 单独查询。

## 前端（utils/hubStore.js）

- 本地 hubStatsV1 的 `day` 是今天：直接使用，不调云函数，切 tab、onShow 都不发请求。
- 云端还停在昨天（别人正在刷新）：5 分钟内不重复请求。
- 领到令牌时，后台发 computeStats，结果只写进本地 hubStatsV1，不更新当前页面，触发者这次看到的仍是历史数据；下次进入首页直接用今天的缓存。
- 下拉刷新或点重试（force）照常请求云端，云端当天有缓存时只是一次读文档。
- 不再处理 refreshIds，也不再逐个发 refreshStats。
- 人数展示规则不变：users 加 100，再向下取整到百位。
