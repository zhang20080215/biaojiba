# 人气统计新旧实现对比

> 2026-10-14 补充：下面的诊断操作是历史排查记录，不再要求用户运行。已对照旧版确认：旧版在客户端查询，豆瓣/IMDb 固定前置；v4 把聚合和兜底放在同一次云函数调用内，函数被终止时无法执行 catch 兜底，租约恢复又会跳过榜单，失败结果可缓存一天。v5 已将这两项改为直接分批数标记并保存进度、按旧公式估算，详见《全局每日统计-上线说明》。已有日志确认数据库聚合超时；本次未调用云端，不能认定当前云端一定发生了函数级终止。

对照来源：Git 提交 `0bdd184` 的 `pages/category/category.js` 与当前 `cloudfunctions/getThemeHub/index.js`。云端证据：用户提供的 2026-10-12 23:34 执行日志，豆瓣电影和 IMDb 均在人数聚合阶段返回 `-501001 / FailedOperation.Timeout`，作品 ID 读取没有报错。

## 已确认的差异

| 项目 | 旧版 | 新版 | 影响 |
| --- | --- | --- | --- |
| 电影标记筛选 | 仅 `movieId in 当前榜单ID` | 额外要求 `status` 为 `watched/wish` 且 `openid` 有效 | 统计口径改变，可能影响索引命中和查询耗时；尚未获得执行计划证据 |
| 去重人数 | 按 `openid` 分组后计数 | 同样按 `openid` 分组后计数 | 两者核心算法相同 |
| 聚合失败 | 分批数标记条数，返回 `ceil(标记条数 / 3)` | 标记 `valid:false` | 旧版即使聚合超时，也可能继续显示估算人数 |
| 展示数字 | 统一加 100，并向下按百位取整 | 真实人数，不加数，不估算 | 旧版“有数字”不足以证明聚合查询成功 |
| ID读取 | 每个主题分别查，在数据库按榜单条件过滤，100 条 offset 分页 | 同集合复用读取结果，再按主题过滤，1000 条游标分页 | 存在执行差异，但这次日志的错误明确发生于人数聚合 |
| 执行位置 | 小程序客户端直接查数据库 | 云函数查数据库并缓存公开汇总 | SDK、权限和运行环境也存在差异 |
| 并发 | 所有主题使用 `Promise.allSettled` 并发 | 4 个统计任务并发 | 新版初始并发更低，不能未经验证就将问题归因于并发增加 |

旧版关键代码：

```js
const m = { [idField]: _.in(ids) };
// 聚合失败后的兜底
return Math.ceil(markCount / 3);
// 展示时继续加数
const displayCount = realUsers + 100;
```

已确认旧版存在以上兜底，但缺少旧版运行日志，不能断定这两个榜单过去一定使用了估算，也不能断定新增查询条件就是本次超时的原因。

## 同条件验证

`getThemeHub` 新增只允许云端控制台/服务端调用的 `compareStats`，仅读取豆瓣电影与 IMDb 两个榜单。它在同一环境、同一批当前榜单 ID 下，依次执行旧版查询条件与新版查询条件，分别返回真实人数、成功状态、耗时或错误码，不估算、不更新人气快照、不返回用户 ID。

由用户重新部署后，在云端测试执行：

```json
{"action":"compareStats"}
```

若两种查询耗时接近，或结果可能受缓存/瞬时压力影响，可以反转执行顺序复核：

```json
{"action":"compareStats","reverse":true}
```

结果解读：

- 旧条件成功、新条件超时：重点检查新增 `status/openid` 条件的查询计划和现有 `Marks` 索引。
- 两者均超时：原有聚合本身也慢，旧版估算兜底能解释界面仍有数字；接着检查基础查询索引及数据库负载。
- 两者均成功：进一步考虑统计批量执行时的竞争或瞬时负载，结合耗时、索引和慢查询日志定位。

暂停此前未验证的降并发、增加超时重试及缩短缓存时间调整，保留已验证的前端重载修复和分项日志。取得对比结果后再确定修复方案。
