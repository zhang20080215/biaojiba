# 豆瓣标记导入 · 可行性验证（2026-11-01）

结论：**可行，建议进入正式实现。** 从云函数出口匿名读用户公开的「看过」列表，大账号整份读完都没被拦。对片率低于原定的 60%，但这条线定得不对，见第三节。

## 一、怎么测的

- 探测代码：`cloudfunctions/probeDoubanImport`（临时云函数，只读、不写库）+ `tools/douban-import-probe/probe.cjs`（本机跑同一份代码）
- 两个来源：
  - 移动端接口 `m.douban.com/rexxar/api/v2/user/{uid}/interests?type=movie&status=done`，JSON，每页 50 条，带总数
  - 桌面「看过」页 `movie.douban.com/people/{uid}/collect`，HTML，每页 15 条
- 两个账号：豆瓣创始人阿北的公开主页 `ahbei`（218 部，冒烟用）、用户本人 `4239269`（580 部）
- 两种出口：本机 IP、云函数出口 IP

## 二、结果

| | 本机 | 云函数出口 |
|---|---|---|
| ahbei（218 部） | 移动端接口 5 页读到 216 部，没被拦 | 第 1 页正常 |
| 4239269（580 部） | 移动端接口 12 页读到 575 部；桌面页 30 页读到 446 部；都没被拦 | **移动端接口 12 页读到 575 部，每页 HTTP 200，每页 0.7~2.2 秒，没被拦** |

- 不需要登录，没有遇到跳转和 403。
- 测试期间云端连续请求约 40 次，全部正常。
- 差的 5 部是豆瓣已下架的条目，接口本身就不返回。

**对片**（读到的豆瓣 ID 去 `movie_facts` 查）：

| 账号 | 能落进至少一个榜单 | 其中豆瓣 TOP250 |
|---|---|---|
| ahbei | 116 / 216（54%） | 58 部 |
| 4239269 | 267 / 575（46%）；按电影算 267 / 548（49%） | **183 部** |

4239269 的 267 部合计要写 542 条标记（一部片在几个榜单就写几条），落点最多的是豆瓣 TOP250 183、Letterboxd 89、史上最佳动画 42。

## 三、关于对片率

原定「对片率 ≥ 60%」看的是用户看过的片有多少在我们库里。但用户看过的片大多不在任何榜单上，这个比例天然不会高，也不影响体验。
真正决定价值的是导入后用户在榜单上**立刻能看到多少进度**：本人账号一导入，豆瓣 TOP250 直接点亮 183/250，另有十几个榜单同时有进度，就是「第一次打开就有进度」的效果。所以这条不作为否决项。

两个已知缺口，阶段二处理或接受：
- **IMDb TOP250 对不上**：`imdb_movies` 没存豆瓣 ID，不在 `movie_facts` 里。一部片若同时在豆瓣榜单，`movie_alias` 扩散不到 IMDb。可接受，或二期补映射。
- **剧集**：27 部剧集一部没落进剧集三榜。这批剧集本来就不在榜单里，属于正常情况。

## 四、风险与对策（进阶段二）

1. **规模化后被封。** 只测了单人、几十次请求，没测多人同时导入。对策：
   - 全局限流：同时最多 N 人导入，每页间隔 ≥ 1 秒
   - 每人每天最多导入 1 次
   - 豆瓣一旦返回要登录、403 或跳转，立即停止并告警，不重试轰炸
   - 上线初期用 `grayBucket` 灰度
2. **用户没公开观影记录**：读到 0 条时提示去豆瓣「设置 → 隐私」打开，或者改用快速补标。
3. **合规**：用户主动发起，只读本人公开数据，不存 uid 和原始列表。提审备注写清用途。
4. **调用超时**：从外面经 HTTP 调用云函数有很短的超时，一次读多页会被掐断（-601008），所以探测改成逐页调用。小程序里用 `wx.cloud.callFunction` 不受这个限制，但正式实现仍按「一次 1~2 页、前端循环」设计，单次调用短，进度条也好做。
